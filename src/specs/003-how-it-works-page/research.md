# Research: How It Works Page

**Decision**: Component abstraction Strategy
**Rationale**: Extracting static Figma absolute positions into reusable atomic components (`JourneySteps`, `EligibilitySection`) with mapped arrays supports modularity and i18next integration natively.
**Alternatives considered**: Hardcoding standard text directly inside the components. Rejected due to the bilingual requirement (NFR-U-02).

**Decision**: Asset Management
**Rationale**: Inline SVGs from Figma add significant bloat. They will be abstracted into dedicated components (e.g., `<IconRegistration />`, `<IconHealth />`) within `src/frontend/src/shared/components/Icons/`.
**Alternatives considered**: Serving SVGs as static files. Rejected because inline SVGs are easier to style with Tailwind CSS utility classes (e.g., color changing on hover).

**Decision**: Layout Refactoring
**Rationale**: Use Tailwind Flexbox and Grid (`grid-cols-1 md:grid-cols-2`) for responsive layouts, eradicating 100% of the monolithic absolute positioning generated by Figma tools.
**Alternatives considered**: Using standard CSS files. Rejected because Tailwind is the mandated constraint in the project constitution.
